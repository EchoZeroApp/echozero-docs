EchoZero uses **five credential types**. Pick the one that matches your integration surface.

## Decision table

| I am building… | Credential | Where to get it |
| --- | --- | --- |
| Server REST integration | API key (`ez_live_`) + secret (`ezs_`), used to sign each request | [Dev Portal](https://devportal.echozero.app) |
| AI assistant / MCP client | OAuth bearer token **or** API key | [OAuth flow](/guides/oauth) or Dev Portal |
| Inbound agent webhook | Per-agent secret (`ezw_`) | Agent create / rotate response |
| Outbound execution callback | Agent `webhookUrl` signing secret | Agent configuration |
| End-user session (rare for devs) | User JWT from `/api/auth/*` | Mobile/web app auth, not typical for bots |

## API key + REST HMAC

Every API-key request must carry `x-api-key`, `x-timestamp` (epoch milliseconds) and `x-signature` (HMAC-SHA256 of `timestamp + METHOD + path + body`, signed with your `ezs_` secret). The secret is required, not optional. A request with only `x-api-key` returns 401.

```bash
# ez is the signing helper from "API keys and HMAC"
ez GET /api/v1/users/me
```

See [API keys + HMAC](/guides/api-keys-hmac) for the helper and the signing rules.

## OAuth (assistants)

PKCE authorization code flow. Access tokens last **1 hour**. There is **no refresh token** today: re-run the consent flow or use long-lived API keys for headless servers.

## Inbound webhook HMAC

```bash
X-EZ-Timestamp: <unix_seconds>
X-EZ-Signature: HMAC_SHA256(ezw_secret, "${ts}.${canonicalJson}")
```

Different algorithm from REST HMAC. See [Webhook security](/guides/webhook-security).

## Scopes

OAuth and API keys share the same scope strings. This is the one scope table for all the docs. It matches the `scopes` enum in the API key schema of the [OpenAPI spec](https://mcp.echozero.app/api/docs-json).

| Scope | Access |
| --- | --- |
| `read:agents` / `write:agents` | Agent CRUD, webhook provisioning, personas |
| `read:strategies` / `write:strategies` | Strategy bots and configuration |
| `read:wallet` / `write:wallet` | Wallet balances, wallet mode, virtual funds |
| `read:trades` | Trade and signal history |
| `read:tokens` | Token metadata and trending |
| `read:earn` | Earnings and claims |
| `read:analytics` | Dashboard analytics |
| `read:ai` / `write:ai` | AI chat and tooling |
| `read:notifications` / `write:notifications` | Notifications and notification settings |
| `admin:*` | Platform admin only. Cannot be created through the API and is not available via OAuth |

Legacy scope names are also in the API's scope list: `agents:read`, `agents:write`, `trades:read`, `trades:execute`, `bots:read`, `bots:write`, `marketplace:read` and `ai:chat`. Prefer the `read:*` / `write:*` names. The published assistant directory manifests do not request `trades:execute` or the legacy names.

The API reference shows the scope a route needs where the spec states one. Where it does not, call the route with a test key and read the 403 if you lack it.

## MCP authentication

Send the same API key or OAuth token on **every** MCP request, including `initialize`. Sessions are credential-bound. See [MCP Server](/guides/mcp).

## Protected endpoints

All `/api/v1/*` routes (except public marketplace browse and inbound webhooks) require authentication. The API Reference playground may label auth as optional for try-it convenience; production calls **must** include credentials.
