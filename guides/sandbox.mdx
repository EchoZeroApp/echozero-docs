title: Sandbox testing
description: Test integrations against the public EchoZero API without affecting live subscribers or executing real trades.
---

External developers test against the **production API host** - there is no separate public staging environment and you do not need access to EchoZero source code.

**Base URL:** `https://mcp.echozero.app/api`

## 1. Create a developer account and API key

1. Sign in at [devportal.echozero.app](https://devportal.echozero.app).
2. Register as a developer and create an API key.
3. Export the key and its secret locally:

```bash
export EZ_API_KEY="ez_live_..."
export EZ_SECRET="ezs_..."
```

Every API-key request must be signed with the secret, so the examples below use the `ez` helper:

```bash
# Signed REST helper: ez METHOD PATH [JSON_BODY]
# Needs EZ_API_KEY (ez_live_...), EZ_SECRET (ezs_...) and jq. Works in bash and zsh.
# The body is compacted with jq -c, and that same compact string is signed and sent.
ez() {
  local method="$1" req_path="$2" body="${3:-}"
  local ts sig
  local args=()
  if [ -n "$body" ]; then
    body=$(printf '%s' "$body" | jq -c .) || return 1
    args=(-d "$body")
  fi
  ts=$(python3 -c 'import time;print(int(time.time()*1000))')
  sig=$(printf '%s' "${ts}${method}${req_path}${body}" | openssl dgst -sha256 -hmac "$EZ_SECRET" | awk '{print $NF}')
  curl -sS -X "$method" "https://mcp.echozero.app${req_path}" \
    -H "x-api-key: $EZ_API_KEY" \
    -H "x-timestamp: $ts" \
    -H "x-signature: $sig" \
    -H "x-ez-mcp-client: ${EZ_CLIENT:-my-integration}" \
    -H "Content-Type: application/json" \
    "${args[@]}"
}
```

See [API keys and HMAC](/guides/api-keys-hmac) for how signing works.

## 2. Dry-run sandbox endpoints

The **Sandbox** API group provides dry-run simulators - they validate ownership and return simulated results with **no real execution**.

### Simulate a trade for your agent

```bash
ez POST "/api/sandbox/agents/$AGENT_ID/trade" '{
  "pair": "SOL/USDC",
  "amount": 100,
  "action": "BUY"
}'
```

### Simulate signal parsing for an agent

```bash
ez POST "/api/sandbox/agents/$AGENT_ID/signals/simulate" '{
  "message": "Buy SOL at $145, TP $160, SL $138"
}'
```

### List sandbox signal history

```bash
ez GET "/api/sandbox/agents/$AGENT_ID/signals"
```

The response is `data.items` plus `data.pagination`. The spec lists no paging query parameters for this route, so do not rely on `page` or `limit`.

See the **Sandbox** tag in the API Reference sidebar for full request/response schemas.

## 3. Virtual wallet (paper trading)

Switch to virtual wallet mode and add simulated funds before testing buy/sell flows:

```bash
# Toggle to virtual mode
ez POST /api/v1/wallet/mode '{ "isVirtualMode": true }'

# Add virtual USDC balance
ez POST /api/v1/wallet/virtual/add-funds '{ "amountInUsdc": 1000 }'
```

Virtual trades use simulated balances - no on-chain execution. `amountInSol` is deprecated; use `amountInUsdc`.

## 4. Portal demo signals

To record a demo signal row for an agent (isolated from live subscriber execution), use the route below. It is not in the public API spec, so its body is undocumented. The `developerAgentId` field name here is unconfirmed (other material may call it `agentId`). Treat this call as unsupported and prefer the sandbox endpoints above:

```bash
ez POST /api/dev/trade-signals '{
  "developerAgentId": "'"$AGENT_ID"'",
  "action": "buy",
  "tokenAddress": "So11111111111111111111111111111111111111112",
  "amount": 100
}'
```

Demo signals appear in developer signal history but do not trigger the live trade bridge.

## 5. Test inbound webhook signing

Create a webhook agent (`signalSourceKind: webhook`, with an `agentVenue`) in the Dev Portal or through the API. Save the `inboundWebhookSigningSecretReveal` (`ezw_...`) shown once at creation.

Inbound signals use the agent's `ezw_` secret, a timestamp in seconds, and canonical JSON (keys sorted alphabetically). This helper does all three:

```bash
# Signed inbound-signal helper: ezw '<json body>'
# Needs AGENT_ID, EZW_SECRET (ezw_...) and jq. Works in bash and zsh.
ezw() {
  local canon ts sig
  canon=$(printf '%s' "$1" | jq -S -c .)   # sorted keys, compact
  ts=$(date +%s)                            # epoch seconds
  sig=$(printf '%s' "${ts}.${canon}" | openssl dgst -sha256 -hmac "$EZW_SECRET" | awk '{print $NF}')
  curl -sS -X POST "https://mcp.echozero.app/api/public/agent-signals/$AGENT_ID" \
    -H "Content-Type: application/json" \
    -H "X-EZ-Timestamp: $ts" \
    -H "X-EZ-Signature: $sig" \
    -d "$canon"
}
```

<Note>
Write numbers in plain form (`100`, `100.5`), not `1.0`, `100.50` or `1E+3`. `jq` keeps numbers as typed, but the server re-serialises them the JavaScript way, so the signature would not match. Send only documented fields too: the server drops unknown top-level fields before it verifies the signature, and `jq` would sign them. If you need arbitrary numbers, use an SDK.
</Note>

```bash
export AGENT_ID="<agent id>"
export EZW_SECRET="ezw_..."

ezw '{"text":"BUY SOL $100","idempotencyKey":"sandbox-001"}'
```

Use [virtual wallet mode](#3-virtual-wallet-paper-trading) so execution uses simulated balances. Full signing details are in [Webhook security](/guides/webhook-security).

## 6. Dev Portal UI

Many flows (agent setup, signal preview, subscriber analytics) can also be exercised from the [Dev Portal](https://devportal.echozero.app) before you wire up production bots.

Use a dedicated test agent with no real subscribers while iterating. When you are ready for live execution, switch to production webhook or structured signal ingestion paths documented in the [Signal envelope](/guides/signal-envelope) and [Webhook security](/guides/webhook-security) guides.
