description: Authorization code + PKCE for AI assistant and CLI clients.

EchoZero supports OAuth 2.1 authorization code with PKCE for clients that cannot safely store long-lived API keys - Claude connectors, ChatGPT apps, local CLIs, and directory integrations.

## Endpoints

| Step | Method | URL |
| --- | --- | --- |
| Client lookup | `GET` | `https://mcp.echozero.app/oauth/client` |
| Authorize | `GET` | `https://mcp.echozero.app/oauth/authorize` |
| Approve (Dev Portal) | `POST` | `https://mcp.echozero.app/oauth/authorize/approve` |
| Token | `POST` | `https://mcp.echozero.app/oauth/token` |
| Introspect | `POST` | `https://mcp.echozero.app/oauth/introspect` |
| Verify status | `GET` | `https://mcp.echozero.app/status` |

User consent is handled in the Dev Portal at [devportal.echozero.app/mcp/oauth/authorize](https://devportal.echozero.app/mcp/oauth/authorize). Users approve from their saved portal session - do not ask them to copy JWTs from browser devtools.

## PKCE parameters

| Parameter | Required | Value |
| --- | --- | --- |
| `response_type` | Yes | `code` |
| `client_id` | Yes | Registered client id (e.g. `echozero-cli`) |
| `redirect_uri` | Yes | Must match a registered redirect URI exactly |
| `scope` | Yes | Space-delimited OAuth scopes (see below) |
| `state` | Yes | Opaque CSRF token - validate on callback |
| `code_challenge` | Yes | `BASE64URL(SHA256(code_verifier))` |
| `code_challenge_method` | Yes | `S256` |

Generate a `code_verifier` (43-128 random characters) and keep it secret until token exchange.

## Browser consent flow

<Steps>
  <Step title="Redirect to authorize">
    Send the user to `GET https://mcp.echozero.app/oauth/authorize` with PKCE `code_challenge`, `state`, `scope`, and `redirect_uri`.

    ```bash
    # Example authorize URL (build in your app)
    https://mcp.echozero.app/oauth/authorize\
      ?response_type=code\
      &client_id=echozero-cli\
      &redirect_uri=http://127.0.0.1:8765/callback\
      &scope=read:agents%20read:wallet\
      &state=random-csrf-token\
      &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM\
      &code_challenge_method=S256
    ```
  </Step>
  <Step title="User approves in Dev Portal">
    EchoZero redirects to the Dev Portal consent page. If the user is not signed in, they authenticate first, then approve the requested scopes.
  </Step>
  <Step title="Receive authorization code">
    EchoZero redirects back to your `redirect_uri` with `?code=...&state=...`. Verify `state` matches what you sent.
  </Step>
  <Step title="Exchange code for token">
    ```bash
    curl -sS -X POST https://mcp.echozero.app/oauth/token \
      -H "Content-Type: application/json" \
      -d '{
        "grant_type": "authorization_code",
        "code": "<authorization_code>",
        "redirect_uri": "http://127.0.0.1:8765/callback",
        "client_id": "echozero-cli",
        "code_verifier": "<your_code_verifier>"
      }'
    ```

    Response:

    ```json
    {
      "access_token": "ez_oauth_...",
      "token_type": "Bearer",
      "expires_in": 3600,
      "scope": "read:agents read:wallet"
    }
    ```
  </Step>
  <Step title="Call protected APIs">
    Send `Authorization: Bearer <access_token>` on REST and MCP requests.
  </Step>
</Steps>

## Verify the token

After login, confirm the token is active:

```bash
curl -sS https://mcp.echozero.app/status \
  -H "Authorization: Bearer $OAUTH_TOKEN"
```

For server-side validation without calling user-scoped routes:

```bash
curl -sS -X POST https://mcp.echozero.app/oauth/introspect \
  -H "Content-Type: application/json" \
  -d '{ "token": "'"$OAUTH_TOKEN"'" }'
```

It returns HTTP **201** (not 200) with the standard success envelope. For a valid token:

```json
{ "success": true, "data": { "active": true, "sub": "...", "client_id": "...", "scope": "...", "exp": 1790000000 } }
```

For an unknown or expired token, `data` is `{ "active": false }`.

## OAuth scopes

Scopes map to API key permissions. Request only what your integration needs. The single scope table, with the full list, is in [Authentication overview](/guides/authentication#scopes). `admin:*` is not available via OAuth. The published directory manifests request the `read:` and `write:` scopes and do not include `trades:execute`.

## Token lifetime and refresh

| Token | TTL | Notes |
| --- | --- | --- |
| Authorization code | **5 minutes** | Single use; exchanged immediately |
| Access token | **1 hour** (`expires_in: 3600`) | No `refresh_token` is issued today |

When the access token expires, **re-run the PKCE consent flow** or use a long-lived **API key** for headless servers. There is no `offline_access` or refresh grant at this time.

### `code_verifier` requirements

43-128 characters from `[A-Z]`, `[a-z]`, `[0-9]`, `.`, `-`, `_`, `~` (unreserved URI characters).

## OAuth error responses

OAuth errors use the same envelope as the rest of the API, not the bare `error` / `error_description` fields from the OAuth spec. A generic OAuth library will not parse them. Match on the HTTP status and `error.code`.

```json
{
  "success": false,
  "error": {
    "code": "BAD_REQUEST",
    "message": "redirect_uri does not match registered client \"EchoZero CLI\""
  }
}
```

| Condition | HTTP | Behavior |
| --- | --- | --- |
| Wrong `redirect_uri` | 400 | `BAD_REQUEST`, message `redirect_uri does not match registered client "<client name>"` |
| Missing or invalid parameters | 400 | `BAD_REQUEST`, with the validator messages joined into one string, for example `response_type must be one of the following values: code, client_id must be a string, ...` |
| Unsupported `grant_type` (for example `refresh_token`) | 400 | `BAD_REQUEST`, `grant_type must be one of: authorization_code` |
| Expired or reused code, or PKCE mismatch | 400 | `BAD_REQUEST`. The message text can change, so do not match on it |
| Invalid `state` on callback | none | Your app should reject the callback |

## MCP with OAuth

OAuth tokens work on MCP the same way as API keys:

1. `POST https://mcp.echozero.app/mcp` with `Authorization: Bearer <access_token>` on **every** request, including `initialize`.
2. Save the `mcp-session-id` response header from `initialize`.
3. Send `mcp-session-id: <session>` on subsequent MCP calls (`tools/list`, `tools/call`, SSE stream, etc.).

<Warning>
MCP sessions are **bound to the credential** used at `initialize`. Switching API keys or OAuth tokens while reusing the same `mcp-session-id` returns **403** with JSON-RPC error code `-32002`.
</Warning>

See the [MCP Server guide](/guides/mcp) for a full `initialize` example.

## Assistant setup

The `ez` CLI runs this PKCE flow for you with the `echozero-cli` client and wires up your assistant:

```bash
npx @echozero/ez login --client claude    # or: codex, openclaw
```

The skills pack (`EchoZeroApp/skills`) is not public yet.

## Directory integrations

For ChatGPT, Claude, Gemini, and other assistant directories, use connector metadata from:

```
https://mcp.echozero.app/public/index.json
```

Per-platform manifests are individual files with the authorize URL, token URL, and recommended scope lists:

- [`/public/directory/chatgpt/ai-plugin.json`](https://mcp.echozero.app/public/directory/chatgpt/ai-plugin.json)
- [`/public/directory/claude/connector.json`](https://mcp.echozero.app/public/directory/claude/connector.json)
- [`/public/directory/gemini/extension.json`](https://mcp.echozero.app/public/directory/gemini/extension.json)

`index.json` lists the others. There is no index page at `/public/directory/{platform}/`.
