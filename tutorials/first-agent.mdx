This tutorial walks through the full integration path: developer account → webhook agent → virtual wallet → signed signal → lifecycle event.

**Time:** ~15 minutes  
**Prerequisites:** [Dev Portal](https://devportal.echozero.app) account, `curl`, `openssl`, `python3` and `jq`

## 1. Register, create an API key and set up signing

Sign in at [devportal.echozero.app](https://devportal.echozero.app), register as a developer, and create an API key. Copy **`ez_live_...`** and **`ezs_...`** immediately (the secret is shown once).

```bash
export EZ_API_KEY="ez_live_..."
export EZ_SECRET="ezs_..."
```

Every REST call made with an API key must be signed, so paste this helper into your shell. It adds `x-timestamp` and `x-signature` for you. The rules are in [API keys and HMAC](/guides/api-keys-hmac).

```bash
# Signed REST helper: ez METHOD PATH [JSON_BODY]
# Needs EZ_API_KEY (ez_live_...), EZ_SECRET (ezs_...) and jq. Works in bash and zsh.
# The body is compacted with jq -c, and that same compact string is signed and sent.
ez() {
  local method="$1" req_path="$2" body="${3:-}"
  local ts sig
  local args=()
  if [ -n "$body" ]; then
    body=$(printf '%s' "$body" | jq -c .) || return 1
    args=(-d "$body")
  fi
  ts=$(python3 -c 'import time;print(int(time.time()*1000))')
  sig=$(printf '%s' "${ts}${method}${req_path}${body}" | openssl dgst -sha256 -hmac "$EZ_SECRET" | awk '{print $NF}')
  curl -sS -X "$method" "https://mcp.echozero.app${req_path}" \
    -H "x-api-key: $EZ_API_KEY" \
    -H "x-timestamp: $ts" \
    -H "x-signature: $sig" \
    -H "x-ez-mcp-client: ${EZ_CLIENT:-my-integration}" \
    -H "Content-Type: application/json" \
    "${args[@]}"
}
```

<Check>
You have a developer API key pair saved locally and the `ez` helper defined. `ez GET /api/v1/users/me` returns your user.
</Check>

## 2. Create a webhook agent

```bash
ez POST /api/v1/agents '{
  "name": "Tutorial Webhook",
  "description": "First integration test",
  "signalSourceKind": "webhook",
  "agentVenue": "JUPITER",
  "isDraft": false
}'
```

<Note>
Agent create calls (`POST /api/v1/agents`) carry an `x-ez-mcp-client` header with a short label for your client. The `ez` helper sends it for you (set `EZ_CLIENT` to change the label). The API spec lists it as required on this route. Whether the server enforces it is not confirmed, so include it.
</Note>

Things to know before you run it:

- **`name`** is 20 characters at most. "Tutorial Webhook" is 16.
- **`agentVenue`** is `JUPITER` (Solana spot) or `HYPERLIQUID` (perpetuals). You cannot change it after creation. For Hyperliquid, see the [Hyperliquid recipe](/recipes/hyperliquid-perp) for the extra field the create call needs.

**Expected response (abbreviated):**

```json
{
  "success": true,
  "data": {
    "id": "674a1b2c3d4e5f6789012345",
    "name": "Tutorial Webhook",
    "signalSourceKind": "webhook",
    "inboundWebhookSigningSecretReveal": "ezw_...",
    "inboundSignalsHttpUrl": "https://mcp.echozero.app/api/public/agent-signals/674a1b2c3d4e5f6789012345"
  }
}
```

<Warning>
Save `inboundWebhookSigningSecretReveal` (`ezw_...`) now. It is never returned again. Rotate it with `PATCH /api/v1/agents/{id}` and `{ "rotateInboundWebhookSigningSecret": true }` if lost.
</Warning>

```bash
export AGENT_ID="<id from response>"
export EZW_SECRET="<inboundWebhookSigningSecretReveal>"
```

<Note>
A new agent is private: it is not on the marketplace until you send `isPublic: true` and staff approve the listing (see [Agent lifecycle](/guides/agent-lifecycle)). If a signal comes back `skipped` with `agent_status_blocked`, the agent's status does not allow execution yet. Check it with `ez GET /api/v1/agents/$AGENT_ID`. Use [virtual wallet mode](#3-enable-virtual-wallet) and the [sandbox endpoints](/guides/sandbox) to test without real money.
</Note>

## 3. Enable virtual wallet

```bash
ez POST /api/v1/wallet/mode '{ "isVirtualMode": true }'
```

```json
{ "success": true, "data": { "isVirtualMode": true } }
```

```bash
ez POST /api/v1/wallet/virtual/add-funds '{ "amountInUsdc": 1000 }'
```

`amountInSol` still works but is deprecated. Use `amountInUsdc`.

## 4. Send a signed entry signal

Inbound signals are signed with the agent's `ezw_` secret, not your API secret. The signature covers `${timestamp}.${canonicalJson}`, where the timestamp is in seconds and the JSON has its keys sorted alphabetically at every level. This helper does both:

```bash
# Signed inbound-signal helper: ezw '<json body>'
# Needs AGENT_ID, EZW_SECRET (ezw_...) and jq. Works in bash and zsh.
ezw() {
  local canon ts sig
  canon=$(printf '%s' "$1" | jq -S -c .)   # sorted keys, compact
  ts=$(date +%s)                            # epoch seconds
  sig=$(printf '%s' "${ts}.${canon}" | openssl dgst -sha256 -hmac "$EZW_SECRET" | awk '{print $NF}')
  curl -sS -X POST "https://mcp.echozero.app/api/public/agent-signals/$AGENT_ID" \
    -H "Content-Type: application/json" \
    -H "X-EZ-Timestamp: $ts" \
    -H "X-EZ-Signature: $sig" \
    -d "$canon"
}
```

<Note>
Write numbers in plain form (`100`, `100.5`), not `1.0`, `100.50` or `1E+3`. `jq` keeps numbers as typed, but the server re-serialises them the JavaScript way, so the signature would not match. Send only documented fields too: the server drops unknown top-level fields before it verifies the signature, and `jq` would sign them. If you need arbitrary numbers, use an SDK.
</Note>

```bash
ezw '{"text":"BUY SOL $100","idempotencyKey":"tutorial-entry-001"}'
```

The helper signs and sends `{"idempotencyKey":"tutorial-entry-001","text":"BUY SOL $100"}`. `idempotencyKey` comes before `text` because keys are sorted. If you build the signed string by hand, sort the keys the same way or use `jq -S -c`.

**Expected:**

```json
{
  "success": true,
  "data": {
    "outcome": "matched",
    "signalId": "sig_...",
    "status": "..."
  }
}
```

<Check>
You received `outcome: matched` and a `signalId`. That is the success moment.
</Check>

If the agent's status does not allow execution you may see `outcome: skipped` with a `skipReason` such as `agent_status_blocked`.

<Note>
Known issue (EZD-66): a brand-new private webhook agent can currently return 404 instead of `outcome: matched`, because the signal endpoint does not find private agents yet. This is being fixed. If you see a 404 and the `agentId` in the URL is correct, that is the likely cause, not a signing mistake. The [sandbox endpoints](/guides/sandbox) work in the meantime.
</Note>

## 5. Send a lifecycle partial sell (optional)

```bash
ezw '{"eventType":"partial_sell","idempotencyKey":"tutorial-partial-001","positionRef":"tutorial-entry-001","sellSizePct":50,"reasoning":"Taking half off at first target."}'
```

The keys sort as `eventType`, `idempotencyKey`, `positionRef`, `reasoning`, `sellSizePct`; the helper handles that.

<Note>
This step shows the request shape. The [error codes](/guides/error-codes) list `sell_not_available_in_virtual_mode` as an execution outcome, so in virtual mode the signal may be accepted but the sell may not execute. Check `executionResult` in the response and in signal history.
</Note>

## 6. Check signal history

```bash
ez GET "/api/v1/developers/agents/$AGENT_ID/signals/history"
```

The response is `data.items` plus `data.pagination`. See [API conventions](/guides/conventions#pagination).
