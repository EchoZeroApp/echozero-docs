## Step 0: Get your API key and set up signing

1. Sign in at [devportal.echozero.app](https://devportal.echozero.app)
2. Register as a developer
3. Create an API key
4. Copy **`ez_live_...`** and **`ezs_...`** (the secret is shown once)

```bash
export EZ_API_KEY="ez_live_..."
export EZ_SECRET="ezs_..."
```

REST calls made with an API key need three headers: `x-api-key`, `x-timestamp` (epoch milliseconds) and `x-signature` (HMAC-SHA256 of `timestamp + METHOD + path + body`, signed with your `ezs_` secret). Sending only `x-api-key` returns 401. Paste this helper into your shell once and use it for every call below:

```bash
# Signed REST helper: ez METHOD PATH [JSON_BODY]
# Needs EZ_API_KEY (ez_live_...), EZ_SECRET (ezs_...) and jq. Works in bash and zsh.
# The body is compacted with jq -c, and that same compact string is signed and sent.
ez() {
  local method="$1" req_path="$2" body="${3:-}"
  local ts sig
  local args=()
  if [ -n "$body" ]; then
    body=$(printf '%s' "$body" | jq -c .) || return 1
    args=(-d "$body")
  fi
  ts=$(python3 -c 'import time;print(int(time.time()*1000))')
  sig=$(printf '%s' "${ts}${method}${req_path}${body}" | openssl dgst -sha256 -hmac "$EZ_SECRET" | awk '{print $NF}')
  curl -sS -X "$method" "https://mcp.echozero.app${req_path}" \
    -H "x-api-key: $EZ_API_KEY" \
    -H "x-timestamp: $ts" \
    -H "x-signature: $sig" \
    -H "x-ez-mcp-client: ${EZ_CLIENT:-my-integration}" \
    -H "Content-Type: application/json" \
    "${args[@]}"
}
```

It needs `curl`, `openssl` and `python3`, which come with macOS and most Linux systems. See [API keys and HMAC](/guides/api-keys-hmac) for how the signature is built, and the SDKs if you would rather not sign by hand.

## Step 1: Verify the API

The health check is public and needs no key:

```bash
curl -sS https://mcp.echozero.app/api
```

```json
{ "success": true, "data": { "Status": "Success" } }
```

Note the capital `S` in `Status`.

## Step 2: Authenticate

```bash
ez GET /api/v1/users/me
```

**Expected:**

```json
{
  "success": true,
  "data": {
    "id": "...",
    "email": "you@example.com"
  }
}
```

<Check>You are authenticated when `success` is `true` and `data.id` is present.</Check>

Getting **401**? Check that all three headers are sent and that your clock is within 5 minutes. See [Error codes](/guides/error-codes).

## Step 3: Create a webhook agent (optional)

```bash
ez POST /api/v1/agents '{
  "name": "Quickstart Agent",
  "signalSourceKind": "webhook",
  "agentVenue": "JUPITER"
}'
```

<Note>
Agent create calls (`POST /api/v1/agents`) carry an `x-ez-mcp-client` header with a short label for your client. The `ez` helper sends it for you (set `EZ_CLIENT` to change the label). The API spec lists it as required on this route. Whether the server enforces it is not confirmed, so include it.
</Note>

Two fields to get right the first time:

- **`agentVenue`** is `JUPITER` (Solana spot) or `HYPERLIQUID` (perpetuals). It is set at creation and **cannot be changed later**. To use the other venue, create a new agent. For a Hyperliquid agent, also include `"signalExecutionDefaults": { "marketType": "perpetual" }` in the same body. The spec says the server derives the market type from the venue, but older builds rejected Hyperliquid creates without it with a bare 400, so include it. See the [Hyperliquid recipe](/recipes/hyperliquid-perp).
- **`name`** is 20 characters at most.

**Expected (abbreviated):**

```json
{
  "success": true,
  "data": {
    "id": "674a1b2c3d4e5f6789012345",
    "name": "Quickstart Agent",
    "signalSourceKind": "webhook",
    "inboundWebhookSigningSecretReveal": "ezw_...",
    "inboundSignalsHttpUrl": "https://mcp.echozero.app/api/public/agent-signals/674a1b2c3d4e5f6789012345"
  }
}
```

Save `inboundWebhookSigningSecretReveal` (`ezw_...`) from the response. It is shown once.

A new agent is private. It is only listed on the marketplace after you send `isPublic: true` and staff approve it. See [Agent lifecycle](/guides/agent-lifecycle).

## Step 4: Send a test signal

Inbound signals use a different signature from REST calls: the per-agent `ezw_` secret, a timestamp in **seconds**, and the body written as **canonical JSON** (keys sorted alphabetically, compact). `jq -S -c` does that for you. This helper signs and sends in one step:

```bash
# Signed inbound-signal helper: ezw '<json body>'
# Needs AGENT_ID, EZW_SECRET (ezw_...) and jq. Works in bash and zsh.
ezw() {
  local canon ts sig
  canon=$(printf '%s' "$1" | jq -S -c .)   # sorted keys, compact
  ts=$(date +%s)                            # epoch seconds
  sig=$(printf '%s' "${ts}.${canon}" | openssl dgst -sha256 -hmac "$EZW_SECRET" | awk '{print $NF}')
  curl -sS -X POST "https://mcp.echozero.app/api/public/agent-signals/$AGENT_ID" \
    -H "Content-Type: application/json" \
    -H "X-EZ-Timestamp: $ts" \
    -H "X-EZ-Signature: $sig" \
    -d "$canon"
}
```

<Note>
Write numbers in plain form (`100`, `100.5`), not `1.0`, `100.50` or `1E+3`. `jq` keeps numbers as typed, but the server re-serialises them the JavaScript way, so the signature would not match. Send only documented fields too: the server drops unknown top-level fields before it verifies the signature, and `jq` would sign them. If you need arbitrary numbers, use an SDK.
</Note>

```bash
export AGENT_ID="<agent id>"
export EZW_SECRET="<ezw secret>"

ezw '{"text":"BUY SOL $50","idempotencyKey":"quickstart-001"}'
```

The signed text for that body is `{"idempotencyKey":"quickstart-001","text":"BUY SOL $50"}`, with `idempotencyKey` before `text`. If you sign the keys in any other order the server rejects the signature.

Use [virtual wallet mode](/guides/sandbox) so test signals use simulated balances.

**Success:**

```json
{
  "success": true,
  "data": {
    "outcome": "matched",
    "signalId": "sig_..."
  }
}
```

<Note>
Known issue (EZD-66): a brand-new private webhook agent can currently return 404 instead of `outcome: matched`, because the signal endpoint does not find private agents yet. This is being fixed. If you see a 404 and the `agentId` in the URL is correct, that is the likely cause, not a signing mistake. The [sandbox endpoints](/guides/sandbox) work in the meantime.
</Note>

If you get `outcome: skipped`, read `skipReason`. See [Error codes](/guides/error-codes).

## Assistant setup

The `ez` CLI (`@echozero/ez` on npm) signs you in with OAuth and wires up your assistant:

```bash
npx @echozero/ez login --client claude    # or: codex, openclaw
```

The skills pack (`EchoZeroApp/skills`) is not public yet. Until it is, use the CLI, [OAuth](/guides/oauth) or an API key.
